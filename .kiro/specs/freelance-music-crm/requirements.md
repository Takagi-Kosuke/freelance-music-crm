# 要件定義書

## はじめに

本ドキュメントは、フリーランス音楽クリエイター（作曲・ミックス・バンド演奏・楽譜作成など）が個人で使用する案件管理 Web アプリ「FreelanceMusicCRM」の要件を定義する。

作業者（クリエイター本人）がログインして案件を一元管理し、クライアント（ゲスト）からの見積依頼受付〜正式依頼〜作業進捗管理〜請求書発行までのライフサイクルを一貫してサポートする。

---

## 用語集（Glossary）

| 用語 | 定義 |
|---|---|
| **System** | FreelanceMusicCRM アプリケーション全体 |
| **Authenticator** | 認証モジュール。ログイン・セッション管理を担当 |
| **Worker** | 作業者。本システムを管理・操作するフリーランスクリエイター本人 |
| **Client** | クライアント。ゲストとして見積依頼・正式依頼を行う発注者 |
| **QuoteRequest** | クライアントが送信する見積依頼 |
| **QuoteResponse** | 作業者がクライアントへ返答する見積回答（金額・納期等を含む） |
| **Order** | クライアントが見積内容を承認し正式発行した依頼 |
| **Task** | Order に紐づく作業者側のタスクレコード |
| **Invoice** | Order 完了後に発行する請求書 |
| **Calendar** | 希望納期をもとに Task を視覚表示するカレンダービュー |
| **DetailPanel** | タスク詳細を表示するサイドパネル |
| **Notifier** | Discord 通知モジュール |
| **Validator** | クライアント入力値のバリデーションモジュール |
| **PDFGenerator** | 請求書 PDF 生成モジュール |
| **EmailSender** | 請求書メール送信モジュール |
| **OrderCategory** | 依頼区分（作曲・ミックス・バンド演奏・楽譜作成・その他） |

## 要件

### 要件 1: 作業者認証

**ユーザーストーリー:** 作業者として、メールアドレスとパスワードでログインできるようにしたい。そうすることで、案件情報を安全に管理できる。

#### 受け入れ基準

1. WHEN 作業者が有効なメールアドレスとパスワードを入力しログインを実行したとき、THE Authenticator SHALL セッショントークンを発行し、作業者をダッシュボードへ遷移させる。
2. WHEN 作業者が無効なメールアドレスまたは誤ったパスワードを入力しログインを実行したとき、THE Authenticator SHALL 認証エラーメッセージを表示し、セッショントークンを発行しない。
3. THE Authenticator SHALL パスワードを bcrypt 等の不可逆ハッシュアルゴリズムで保存する。
4. WHILE 作業者がログイン中のとき、THE Authenticator SHALL セッションの有効期限を管理し、一定期間操作がない場合にセッションを失効させる。
5. IF 作業者がログインしていない状態で保護されたページへアクセスしたとき、THEN THE Authenticator SHALL ログインページへリダイレクトする。
6. THE System SHALL 作業者アカウント以外のロールによるログインを受け付けない。

---

### 要件 2: クライアントによる見積依頼送信

**ユーザーストーリー:** クライアントとして、ログイン不要で見積依頼を送信したい。そうすることで、手軽に作業者へ依頼の打診ができる。

#### 受け入れ基準

1. THE System SHALL クライアントがログインなしで見積依頼フォームにアクセスできるようにする。
2. WHEN クライアントが見積依頼フォームを送信したとき、THE Validator SHALL 依頼件名・依頼者名・依頼区分・希望納期の各フィールドに値が入力されていることを検証する。
3. IF Validator がバリデーションエラーを検出したとき、THEN THE System SHALL 該当フィールドにエラーメッセージを表示し、送信を中断する。
4. WHEN バリデーションが成功したとき、THE System SHALL QuoteRequest レコードを生成し、作業者へ通知する。
5. THE Validator SHALL ファイルパス（クラウドリンク URL）フィールドが入力された場合、有効な URL 形式であることを検証する。
6. THE Validator SHALL コメントフィールドの文字数が 1000 文字以内であることを検証する。
7. WHEN QuoteRequest が正常に送信されたとき、THE System SHALL クライアントに受付完了メッセージを表示する。

---

### 要件 3: 作業者による見積回答

**ユーザーストーリー:** 作業者として、受信した見積依頼に対して金額・納期等を含む見積回答を提示したい。そうすることで、クライアントに正式依頼の判断材料を提供できる。

#### 受け入れ基準

1. WHEN 作業者がログイン中の状態で QuoteRequest を選択したとき、THE System SHALL 依頼件名・依頼者名・依頼区分・希望納期・ファイルパス・コメントを含む依頼詳細を表示する。
2. WHEN 作業者が見積金額・回答納期・回答コメントを入力して見積回答を送信したとき、THE System SHALL QuoteResponse レコードを生成し、見積金額・回答納期・送信日時を保存する。
3. THE System SHALL 見積金額が 0 円以上の整数であることを検証する。
4. THE System SHALL QuoteRequest 1 件に対して QuoteResponse を 1 件のみ紐付ける。
5. WHEN QuoteResponse が保存されたとき、THE System SHALL クライアントが見積内容を確認できる専用 URL（トークン付き）を生成する。

---

### 要件 4: クライアントによる正式依頼発行

**ユーザーストーリー:** クライアントとして、見積内容を確認して正式に依頼を発行したい。そうすることで、作業者が正式な作業を開始できる。

#### 受け入れ基準

1. WHEN クライアントが専用 URL にアクセスしたとき、THE System SHALL QuoteResponse の詳細（金額・納期・コメント）を表示する。
2. WHEN クライアントが依頼を承認したとき、THE System SHALL Order レコードを生成し、ステータスを「受注済み」に設定する。
3. WHEN Order が生成されたとき、THE System SHALL Order に紐づく Task レコードを作業者側のタスク一覧に登録する。
4. WHEN クライアントが依頼を辞退したとき、THE System SHALL QuoteRequest のステータスを「辞退」に更新し、Task を生成しない。
5. THE System SHALL Order に依頼 ID・依頼件名・依頼者名・依頼区分・希望納期・ファイルパス・コメントを含めて保存する。
6. THE System SHALL 同一 QuoteResponse に対して重複して Order が生成されないようにする。

---

### 要件 5: タスク管理

**ユーザーストーリー:** 作業者として、受注した依頼をタスクとして進捗管理したい。そうすることで、納期遅れや対応漏れを防止できる。

#### 受け入れ基準

1. THE System SHALL Task に「未着手・進行中・完了・キャンセル」のいずれかのステータスを持たせる。
2. WHEN 作業者が Task のステータスを変更したとき、THE System SHALL 変更後のステータスと更新日時を保存する。
3. THE System SHALL Task 一覧に依頼ID・依頼件名・依頼者名・依頼区分・希望納期・ステータスを表示する。
4. WHEN 作業者が依頼区分でフィルタリングを実行したとき、THE System SHALL 指定した依頼区分の Task のみを一覧に表示する。
5. WHEN 作業者が Task をクリックしたとき、THE DetailPanel SHALL Task の全フィールド（依頼ID・依頼件名・依頼者名・依頼区分・希望納期・ファイルパス・コメント・ステータス）を画面右側のサイドパネルに表示する。

---

### 要件 6: カレンダー表示

**ユーザーストーリー:** 作業者として、希望納期をベースにタスクをカレンダー上で確認したい。そうすることで、スケジュールを直感的に把握できる。

#### 受け入れ基準

1. THE Calendar SHALL 月表示・週表示を切り替えられるカレンダーを作業者に提供する。
2. THE Calendar SHALL 各 Task を希望納期の日付のセルに表示する。
3. WHEN 作業者がカレンダー上の Task をクリックしたとき、THE DetailPanel SHALL Task の全フィールドをサイドパネルに表示する。
4. THE Calendar SHALL ステータスが「完了」の Task と「未着手・進行中」の Task を異なる配色で区別して表示する。
5. WHILE DetailPanel が表示中のとき、THE System SHALL カレンダーと DetailPanel を同一画面内に並列表示する。

---

### 要件 7: 依頼区分の管理

**ユーザーストーリー:** 作業者として、依頼区分（作曲・ミックスなど）を随時追加・編集できるようにしたい。そうすることで、業務の変化に柔軟に対応できる。

#### 受け入れ基準

1. THE System SHALL 初期値として「作曲・ミックス・バンド演奏・楽譜作成・その他」の 5 区分を提供する。
2. WHEN 作業者が新しい区分名を入力して追加を実行したとき、THE System SHALL OrderCategory レコードを生成し、依頼区分一覧に追加する。
3. THE System SHALL 区分名が 1 文字以上 50 文字以内であることを検証する。
4. WHEN 作業者が既存の区分名を編集して保存したとき、THE System SHALL 既存の OrderCategory レコードの区分名を更新する。
5. IF 作業者が Task に紐づいている区分を削除しようとしたとき、THEN THE System SHALL 削除を拒否し、「使用中の区分は削除できません」というエラーメッセージを表示する。

---

### 要件 8: 請求書発行

**ユーザーストーリー:** 作業者として、依頼完了後に請求書を発行してクライアントに送付したい。そうすることで、迅速に代金請求ができる。

#### 受け入れ基準

1. WHEN Task のステータスが「完了」になったとき、THE System SHALL 作業者が Invoice を発行できるようにする。
2. WHEN 作業者が Invoice の発行を実行したとき、THE System SHALL Invoice に依頼ID・依頼件名・依頼者名・依頼区分・納品日・請求金額・発行日・作業者情報（氏名・連絡先）を含めて保存する。
3. WHEN 作業者が Invoice の PDF ダウンロードを要求したとき、THE PDFGenerator SHALL Invoice 情報を含む PDF ファイルを生成し、ブラウザにダウンロードさせる。
4. THE PDFGenerator SHALL 生成した PDF が日本語テキストを正常に出力できることを保証する。
5. WHERE メール送信機能が有効な場合、WHEN 作業者が Invoice のメール送信を実行したとき、THE EmailSender SHALL TLS 暗号化通信を使用して Invoice PDF を添付した電子メールをクライアントへ送信する。
6. WHERE メール送信機能が有効な場合、THE EmailSender SHALL 送信元メールアドレスの認証に DKIM または SPF を使用する。
7. THE System SHALL 同一 Task に対して Invoice を 1 件のみ発行できるようにする。

---

### 要件 9: Discord 通知

**ユーザーストーリー:** 作業者として、重要なイベント発生時に Discord へ通知を受け取りたい。そうすることで、アプリを常時開かなくてもリアルタイムで状況を把握できる。

#### 受け入れ基準

1. WHERE Discord 通知が設定されている場合、WHEN 新規 QuoteRequest が生成されたとき、THE Notifier SHALL Discord Webhook URL へ通知メッセージを送信する。
2. WHERE Discord 通知が設定されている場合、WHEN Order が生成されたとき（正式依頼発行時）、THE Notifier SHALL Discord Webhook URL へ通知メッセージを送信する。
3. WHERE Discord 通知が設定されている場合、WHEN Task のステータスが「完了」に変更されたとき、THE Notifier SHALL Discord Webhook URL へ通知メッセージを送信する。
4. IF Notifier が Discord Webhook への送信に失敗したとき、THEN THE Notifier SHALL エラーをログに記録し、システム本体の処理を中断しない。
5. THE System SHALL Discord Webhook URL を作業者が設定・変更できる設定画面を提供する。

---

### 要件 10: レスポンシブ UI / デザインシステム

**ユーザーストーリー:** 作業者として、スマートフォンを含むあらゆる端末で快適にアプリを使用したい。そうすることで、外出先でも案件管理ができる。

#### 受け入れ基準

1. THE System SHALL 画面幅 375px 以上のすべてのビューポートで、レイアウトの崩れなく全機能を提供する。
2. THE System SHALL 白を基調とした背景色と、発色の良いオレンジ（推奨: #FF6B00 ±10%）をアクセントカラーとして使用する。
3. THE System SHALL ボタン・フォーム・テーブルを含むすべての主要 UI コンポーネントにおいて、WCAG 2.1 AA 準拠のコントラスト比（4.5:1 以上）を維持する。
4. WHEN ユーザーがタッチデバイスを使用しているとき、THE System SHALL タップ対象領域を 44px × 44px 以上に確保する。
5. THE System SHALL スマートフォン表示時に、カレンダーを縦スクロール対応のレイアウトで提供する。

---

### 要件 11: 入力バリデーションとセキュリティ

**ユーザーストーリー:** 作業者として、クライアントの入力に起因するセキュリティリスクを排除したい。そうすることで、システムの安全性を保てる。

#### 受け入れ基準

1. THE Validator SHALL クライアントから受信するすべての入力値に対してサーバーサイドバリデーションを実施する。
2. THE System SHALL クライアント入力値をデータベースクエリに使用する際、パラメータ化クエリまたはプリペアドステートメントを使用して SQL インジェクションを防止する。
3. THE System SHALL クライアント入力値を HTML として出力する際、XSS 攻撃を防止するためにエスケープ処理を施す。
4. THE System SHALL API エンドポイントへのリクエストに CSRF トークン検証を実装する。
5. WHEN 作業者が連続して認証に失敗したとき、THE Authenticator SHALL 一定回数（5 回）を超えた場合にアカウントを一時ロックする。
6. THE System SHALL 作業者のみがアクセス可能な API エンドポイントに対して、有効なセッショントークンを持つリクエストのみを処理する。
